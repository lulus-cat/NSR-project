# 전사 파이프라인의 원리

요구사항 2번이 "원리 파악해야함"이었다. 이 문서가 그 답이다.

음성인식이 왜 간호 용어에서 무너지는지, 그걸 고치는 방법이 몇 가지이고 각각 어디까지 되는지,
그리고 이 저장소가 그중 무엇을 구현했는지를 순서대로 적는다.

---

## 1. Whisper는 어떻게 동작하는가

Whisper는 인코더-디코더 트랜스포머다. 처리 흐름은 이렇다.

```
오디오 (16kHz mono)
   ↓  30초 단위로 자르고 패딩
로그-멜 스펙트로그램 (80 mel bins × 3000 frames)
   ↓  Conv1D ×2 → 위치 임베딩
인코더 (self-attention 블록 N개)
   ↓  오디오 표현 (1500 × d)
디코더 (cross-attention으로 오디오를 보면서 토큰을 하나씩 생성)
   ↓
텍스트 토큰 (BPE)
```

**중요한 지점은 디코더가 언어모델이기도 하다는 것이다.**
디코더는 매 스텝에서 `P(다음 토큰 | 지금까지 나온 토큰, 오디오)`를 계산한다.
오디오가 애매하면 앞 토큰들이 만든 언어적 사전확률이 결과를 좌우한다.

디코더 입력의 맨 앞은 특수 토큰들이다.

```
<|startofprev|> ...이전 문맥... <|startoftranscript|> <|ko|> <|transcribe|> <|notimestamps|> ...
```

`<|startofprev|>` 뒤에 우리가 원하는 텍스트를 넣을 수 있다. 이게 `initial_prompt`다.
**즉 프롬프트는 마법이 아니라, 디코더 언어모델의 문맥을 우리가 채워 넣는 것이다.**

## 2. 왜 한국어 간호 대화에서 무너지는가

Whisper의 한국어 학습 데이터는 뉴스·강연·유튜브 자막이 중심이다. 병동 대화는 그 분포 밖에 있다.
구체적으로 네 가지가 겹친다.

### (1) 영문 약어를 한국어 발음으로 읽는다

"브이에스 체크했어?"에서 화자는 V/S를 "브이에스"라고 발음한다.
Whisper 입장에서는 **틀린 게 아니다.** 소리대로 정확히 받아적은 것이다.
그런데 읽는 사람에게는 쓸모가 없다.

이건 모델을 아무리 좋게 해도 안 고쳐진다. 정의상 후처리 문제다.

### (2) 외래어 표기가 흔들린다

`카테터 / 카데터 / 카테타 / 카데타`. 사람도 제각각 쓰고 모델도 제각각 뱉는다.
표기 하나를 정답으로 두면 나머지가 전부 오답이 된다.

### (3) 한국어 음운 변동이 표기를 바꾼다

한국어는 소리 나는 대로 적으면 표기가 달라진다.

| 표기 | 발음 | ASR이 적을 수 있는 것 |
| --- | --- | --- |
| 폴리 삽입 | 폴리 사빕 | "폴리 사빕" |
| 낙상 | 낙쌍 | "낙쌍" |
| 입원 | 이붠 | "이붠" |

문자열로 비교하면 완전히 다른 단어지만, **발음으로 보면 같은 말이다.**

### (4) 평음/격음/경음과 모음 합류

`ㄷ↔ㅌ↔ㄸ`, `ㄱ↔ㅋ↔ㄲ`은 조음 위치가 같아 잡음이 섞이면 헷갈린다.
`ㅐ`와 `ㅔ`는 현대 서울말에서 사실상 합류했다. 모델도 사람도 구분하지 못한다.

## 3. 고칠 수 있는 지점 네 곳

| 지점 | 방법 | 비용 | 이 저장소의 선택 |
| --- | --- | --- | --- |
| 모델 자체 | 파인튜닝 (LoRA 등) | 라벨링된 병동 음성이 필요. 개인정보 문제가 정면으로 걸림 | **안 함** |
| 디코딩 문맥 | `initial_prompt` | 무료, 즉시 | **함** (`buildInitialPrompt`) |
| 디코딩 로짓 | `hotwords` / shallow fusion | 무료, 즉시 | **함** (`buildHotwords`) |
| 출력 텍스트 | 후처리 교정 | 무료, 결정적, 검증 가능 | **함** ← 여기가 주력 |

### 왜 파인튜닝을 안 하는가

이론적으로는 가장 효과가 크다. 그러나 학습 데이터가 곧 **환자 대화 녹음**이다.
이를 수집·라벨링·학습에 쓰려면 개인정보보호법상 요건과 병원 IRB를 통과해야 한다.
개인이 만드는 앱의 범위를 넘는다. 병원 차원의 프로젝트가 된다면 그때 다시 볼 문제다.

### initial_prompt의 한계 — 224 토큰

`<|startofprev|>` 컨텍스트는 **224 토큰으로 잘린다.** 한국어는 음절당 1~2 토큰이므로
실제로 넣을 수 있는 건 100~140 단어 정도다. 사전 전체(수백 개)는 못 들어간다.

그래서 `buildInitialPrompt()`는 우선순위를 매겨 예산 안에 담는다.

- 카테고리 가중치: 투약·응급 > 기구·처치 > 검사·사정 > 업무·역할
  (오인식했을 때 위해가 큰 순서)
- 실제 사용 이력이 있으면 그 가중치가 카테고리 선입견을 이긴다
- **높은 우선순위를 뒤쪽에 배치한다.** 컨텍스트는 앞에서부터 잘리므로 뒤에 있을수록 살아남는다
- 맨 앞에 대화체 한 문장("간호사 인계 대화입니다.")을 둔다.
  용어만 나열하면 Whisper가 프롬프트의 **문체**까지 따라해 출력이 목록처럼 끊긴다

### hotwords의 한계 — 환각

`hotwords`는 디코딩 중 특정 토큰열의 로짓에 보너스를 더한다(shallow fusion).
길이 제약이 덜하지만, 보너스를 크게 주면 **없는 단어를 만들어낸다.**
"그냥 그랬어요"가 "그 CPR 했어요"가 되는 식이다. 그래서 개수 상한(기본 120개)을 둔다.

## 4. 후처리 교정 — 이 저장소의 주력

`packages/core/src/transcription/correct.ts`.

### 4.0 대전제: 전사본은 증거다

이 전사본은 학습자료이면서 동시에 태움 판단의 근거이고, 필요하면 신고 자료가 된다.
그래서 **"읽기 좋게 다듬는 것"과 "말한 내용을 바꾸는 것"을 엄격히 구분한다.**

| 입력 | 처리 | 이유 |
| --- | --- | --- |
| "카데타" | → "카테터" 로 **교정** | 음성인식이 틀린 것 |
| "폴리" | 그대로 두고 **주석만** | 화자가 실제로 그렇게 말한 것 |
| "브이에스" | → "V/S" 로 **표기 변환** | 발화 내용은 같고 표기만 읽기 쉽게 (되돌릴 수 있음) |

이 구분을 위해 사전은 두 종류의 표기를 따로 갖는다.

- `aliases` — 사람이 실제로 그렇게 말하는 표기 (`폴리`, `썩션`, `노티`)
- `misheard` — 음성인식이 잘못 적는 표기 (`포리`, `섹션`, `노디`)

원본(`rawText`)은 어떤 경우에도 보존되고, 모든 교정은 개별 수락/거절이 가능한 레코드로 남는다.

### 4.1 한글 자모 분해

한글 음절은 다음 식으로 만들어진다.

```
code = 0xAC00 + (초성index × 21 + 중성index) × 28 + 종성index
```

역산하면 초/중/종성을 얻는다. 음절 단위로 비교하면 "카테터"와 "카데터"는 서로 다른 두 글자지만,
자모로 펼치면 `ㅋㅏㅌㅔㅌㅓ` vs `ㅋㅏㄷㅔㅌㅓ` — **자모 하나 차이**다.
실제 ASR 오류는 거의 항상 이 수준이다.

### 4.2 음운 변동 정규화

양쪽을 **발음형**으로 바꾼 뒤 비교하면 3-(3)의 문제가 통째로 사라진다.
구현한 규칙(표준 발음법의 주요 항목):

1. 격음화 — 축하 → 추카, 좋고 → 조코
2. 연음 — 입원 → 이붠, 삽입 → 사빕
3. 자음군 단순화 — 겹받침의 대표음
4. 비음화 — 입니다 → 임니다, 작년 → 장년
5. 유음화 — 신라 → 실라
6. 구개음화 — 같이 → 가치
7. 경음화 — 낙상 → 낙쌍
8. 종성 중화 — 밖 → 박, 옷 → 옫

목표는 표준 발음의 완전한 구현이 아니라 **"같게 들리는 두 표기를 같은 문자열로 모으는 것"**이다.

### 4.3 자모 단위 가중 편집거리

일반 편집거리는 모든 치환을 1로 센다. 그러나 실제 혼동은 특정 쌍에 몰려 있다.

| 치환 비용 | 대상 |
| --- | --- |
| 0.3 | 같은 계열 (`ㄷ/ㄸ/ㅌ`, `ㅐ/ㅔ`, `ㅗ/ㅜ`, `ㄴ/ㅁ/ㅇ` …) |
| 0.95 | 그 밖의 자음↔자음, 모음↔모음 |
| 1.2 | 자음↔모음 (사실상 다른 단어) |
| 0.5 | `ㅇ ㅎ ㅡ ㅣ`의 삽입/삭제 (잘 안 들려 누락되기 쉬움) |

인접 전위(transposition)도 센다. "카테터" → "카터테" 같은 뒤바뀜이 실제로 나타난다.

이 가중 덕분에 "카데타↔카테터"의 거리는 크게 줄고 "카데타↔간호사"는 그대로 남는다.
**오탐을 늘리지 않고 재현율만 오른다.**

### 4.4 한글 알파벳 읽기 → 영문 약어 복원

3-(1)에 대한 답이다.

```
"에이비지에이"
  → 알파벳 읽기 사전으로 파싱 (최장일치 + 백트래킹)
  → 에이|비|지|에이 = "ABGA"
  → 사전에 ABGA가 존재하는가? → 예 → 채택
```

읽기가 중의적이므로(`씨`=C 또는 S, `지`=G 또는 Z, `비`=B 또는 V) 가능한 조합을 전부 만든 뒤
**사전에 실재하는 약어만 남긴다.** 이 화이트리스트 필터가 오탐을 막는 유일한 장치다.
없으면 "이오"가 EO로, "아이"가 AI로 바뀌는 참사가 난다.

### 4.5 매칭 단위 — 어절과 조사 절단

한국어는 `용어 + 조사/어미`가 한 어절로 붙는다. "석션을", "드레싱했어요".
그래서 각 어절 시작점에서 마지막 어절의 꼬리를 0~3음절 잘라가며 시도한다.

```
"드레싱했어요" → "드레싱했어요" / "드레싱했어" / "드레싱했" / "드레싱" ← 매칭
```

여러 어절에 걸친 용어("정맥 측관 주입")를 위해 최대 3어절까지 확장한다.

### 4.6 짧은 말에 대한 처리

2음절 용어(`노티` `폴리` `오더` `인계` `옵세`)는 이 도메인의 핵심이다.
그런데 짧을수록 우연히 걸릴 확률도 높다.

배제하는 대신 **짧을수록 높은 신뢰도를 요구한다.** 2음절은 0.92 이상, 3음절 이상은 0.90 이상.

### 4.7 사용자 교정 학습

내장 사전은 "일반적인 병동"을 가정한다. 실제 오인식은 사람마다 다르다.
억양, 마이크 위치, 그 병동에서만 쓰는 약칭은 미리 채울 수 없다.

그래서 사용자가 화면에서 한 글자라도 고치면 기록해둔다.
같은 교정이 2회 반복되면 규칙으로 승격되어 다음 전사부터 자동 적용된다.
쓸수록 **그 사람 전용 후처리기**가 만들어진다.

안전장치: 최소 반복 횟수, 문장 단위 교정 제외(단어 수준만), 목록에서 삭제 가능, 오래된 규칙 정리.

## 5. 규칙으로 못 푸는 것 — 문맥

`D/C`는 discharge(퇴원)일 수도 discontinue(중단)일 수도 있다.
`I/O`가 intake&output인지 in/out인지도 문맥이 정한다.
**이건 규칙으로 못 푼다. 문맥을 보는 모델이 필요하다.**

그래서 선택적 LLM 후편집 단계를 둔다 (`apps/mobile/src/services/llm.ts`).

- 입력: 규칙 교정을 마친 텍스트 + 용어집
- 출력: 문맥 의존 표기 확정, 문장 경계 정리, 화자 발화 구조화
- 용어집은 요청마다 바뀌지 않으므로 **프롬프트 캐시의 안정 접두부**로 둔다.
  긴 용어집을 매번 전액 과금하지 않기 위한 것이고, 캐시가 깨지지 않도록 정렬 순서를 고정한다
- **비식별화가 먼저 적용된다.** 이 단계는 기본 꺼짐이며, 켜는 것은 사용자의 명시적 선택이다

## 6. 화자분리 (diarization)

"누가 말했는가"는 태움 판단에 필수다. 같은 문장도 본인이 한 말이면 채점 대상이 아니다.

- 세그먼트별 화자 임베딩을 뽑아 클러스터링한다 (pyannote 계열, 온디바이스 경량 모델)
- 결과는 `spk_0`, `spk_1` 같은 익명 클러스터다. **역할 라벨은 사용자가 붙인다**
- 본인 음성은 최초 설정 시 등록해 자동 식별한다.
  이건 태움 채점의 정확도뿐 아니라 **통신비밀보호법 대응**에도 쓰인다 —
  (한때 '본인 없는 구간 자동 폐기'의 근거로 두었으나 화자 판별이 불가능해 철회 — docs/01 참고)

## 7. 평가 — 무엇을 재야 하는가

CER/WER만 보면 안 된다. 전체 문자 오류율이 5%여도, 그 5%가 전부 약물명이면 쓸모없는 시스템이다.

이 도메인에서 실제로 봐야 할 지표:

| 지표 | 정의 | 왜 |
| --- | --- | --- |
| **용어 재현율** | 실제 발화된 사전 용어 중 올바르게 잡힌 비율 | 이게 앱의 존재 이유다 |
| **용어 정밀도** | 잡았다고 한 것 중 실제로 맞은 비율 | 오탐은 잘못된 학습카드를 만든다 |
| **과교정률** | 맞게 적힌 것을 틀리게 바꾼 비율 | 가장 나쁜 실패. 원문 신뢰를 깨뜨린다 |
| **약어 복원 정확도** | 한글 읽기 → 영문 약어 변환의 정확도 | |
| CER/WER | 참고용 | 단독으로는 의미가 얕다 |

`packages/core/test/transcription.test.ts`가 이 성질들을 회귀 테스트로 고정한다.
특히 "화자가 실제로 쓴 은어는 바꾸지 않는다"와 "오인식 교정의 목적지는 다른 오인식 표기가 아니다"는
과교정을 막는 안전망이다.

## 8. 온디바이스 vs 클라우드

| | 온디바이스 (whisper.cpp) | 클라우드 |
| --- | --- | --- |
| 정확도 | small/medium 양자화 기준 낮음 | large-v3 기준 높음 |
| 속도 | 최신 폰에서 실시간의 2~5배 | 훨씬 빠름 |
| 개인정보 | 환자 정보가 기기를 벗어나지 않음 | 민감정보의 외부 전송 |
| 비용 | 0 | 시간당 과금 |
| 오프라인 | 됨 | 안 됨 |

**기본값은 온디바이스다.** 정확도를 조금 잃더라도 환자 정보를 내보내지 않는 쪽을 택한다.
8시간 녹음은 VAD로 무음을 걷어내면 실제 발화가 1~2시간 수준이라, 오프 시간에 배치 처리하면 감당된다.

클라우드 전사는 옵트인이며, 켤 때 비식별화가 자동 적용되고 의료법 제19조 고지가 다시 뜬다.

## 9. 파이프라인 전체

```
녹음 (30분 분할, 근무시간 자동)
   ↓
VAD — 무음 제거 (전사량 1/4로, 환각도 감소)
   ↓
화자분리 — spk_0 / spk_1 …
   ↓
본인 음성 식별 → 본인 미포함 구간 폐기 (통비법 대응)
   ↓
ASR (온디바이스 Whisper)
   ├─ initial_prompt : 우선순위 용어 목록 (224토큰 예산)
   ├─ hotwords       : 로짓 편향 (상한 120)
   └─ temperature 0  : 결정적 디코딩. 의료 전사에 창의성은 필요 없다
   ↓
후처리 교정  ← packages/core/src/transcription/correct.ts
   ├─ 0. 사용자 학습 규칙
   ├─ 1. 한글 알파벳 읽기 → 영문 약어
   ├─ 2. misheard 표기 → 실제 발화 표기
   ├─ 3. 발음 유사 매칭 (음운 정규화 + 자모 가중 편집거리)
   └─ 4. 용어 주석 (교정하지 않고 뜻만 붙임)
   ↓
[선택] LLM 후편집 — 문맥 의존 표기, 문장 구조화 (비식별화 후)
   ↓
   ├─→ 학습카드 생성   (study/cards.ts)
   ├─→ 태움 지표       (taeum/score.ts)
   └─→ 근무 보고서     (study/report.ts)
```
