# 교정이 실제로 어떻게 도는가

이 저장소가 전사본을 고치는 방법. 사람이 손으로 교정할 때도 같은 순서로 생각한다.
코드는 `packages/core/src/transcription/correct.ts`, 사전은 `packages/core/src/lexicon/`.

## 대전제 — 이 로직은 휘스퍼 전사본에만 쓴다

`misheard` 목록은 **휘스퍼가 어떻게 틀리는지**의 기록이다. "대노관"=데노간, "감동사"=간병사는
휘스퍼의 습관이지 한국어의 성질이 아니다. 제미나이·클로바노트는 다르게 틀린다 — 그 목록을
들이대면 맞지도 않고 엉뚱한 말을 바꾼다.

- 코드에서는 `correctTranscript(text, { asrEngine })` 로 가른다. `"whisper"`(기본값)일 때만
  misheard 경로가 돈다. 제미나이 전사면 앱이 `"other"` 를 넘긴다.
- 사람이 교정할 때도 같다. **다른 엔진의 전사본이면 `confirmed-rules.md` 의 대응표를 그대로
  적용하지 않는다.** 문맥으로 판단하고, 그 엔진의 오류 습관은 따로 쌓는다.
- 엔진과 무관한 것은 그대로 쓴다: 사전 표기·별칭(사람이 실제로 그렇게 말하는 말), 약어 읽기,
  사용자 교정 이력.

## 순서 — 앞 단계가 뒤 단계를 막는다

### 0. 사용자 교정 이력 (`CorrectionMemory`)

본인이 전에 직접 고친 것을 사전보다 **먼저** 적용한다. 본인 병동의 발음·은어는 사전보다
사용자 이력이 정확하다. `minCount` 번 이상 같은 교정을 한 것만 규칙이 된다.

### 1. 문장으로 나눈다

휘스퍼가 주는 것은 30초짜리 덩어리이지 문장이 아니다. **교정보다 먼저** 나눠야 교정 위치가
문장 기준으로 잡힌다. 같은 문장이 3번 이상 연달아 나오면 디코더 환각으로 보고 접는다
("네. 네. 네." 수십 줄이 1,600문장을 만든 실사례).

### 2. 어절 묶음으로 사전을 찾는다

한 어절씩이 아니라 **최대 3어절까지 묶어** 본다. "팁 컬처", "정규 오더" 처럼 띄어 쓰는 용어가
있기 때문이다. 긴 것부터 본다 — "신전 도서"가 "신전"보다 먼저 잡혀야 한다.

찾는 방법은 네 가지이고, 확실한 순서다.

| 경로 | 무엇 | 신뢰도 |
| --- | --- | --- |
| `exact` | 표기 그대로 | 1 |
| `misheard` | 확정된 오인식 표기 (**휘스퍼 전용**) | 1 |
| `initialism` | 약어의 한글 읽기 ("브이에스"→V/S) | 1 |
| `phonetic` | 자모 편집거리로 비슷한 말 | 0~1 |

### 3. 발음 매칭에는 문턱이 있다

`phonetic` 은 우연히 걸린다. 그래서 문턱을 둔다.

- 기본 0.9. **2음절 이하는 0.95** — 0.92 였을 때 "아니"↔"아이"(0.925)가 걸려 실제 전사본의
  "아니라고" 가 "아이라고" 로 바뀌었다. 자모 하나 차이의 2음절은 발음만으로 못 가른다.
- **두 어절 이상 걸치는 후보는 0.95 이상**만.
- `COMMON_WORDS` 에 있는 흔한 일반어는 발음이 맞아도 바꾸지 않는다. 그 목록과 이유는
  `packages/core/src/lexicon/common-words.ts` 와 `AMBIGUOUS_NOTES` 에 있다.
- 조사가 붙은 채로 겨우 비슷해진 것은 거부한다 ("설명은"이 "천명음"으로 바뀐 사고).
- 꼬리를 자를 때는 **실제 조사·어미로 시작할 때만** 자른다 (낱말 끝 "티"를 조사로 보고
  "티오티"를 "TO티"로 만든 사고).

### 4. 약어 표기를 정한다

`abbreviationStyle: "latin"` 이면 한글 읽기를 라틴 약어로 바꾼다("브이에스"→"V/S").
`"keep"` 이면 원문을 두고 주석만 단다 — 말한 그대로가 중요할 때.

## 규칙으로 고치지 않는 것

- **화자가 실제로 한 말.** 은어("폴리")·상표명("큐프린")·사투리·군말은 그대로 둔다.
- **뜻이 문맥에 따라 갈리는 말.** "시기"(식이/때), "발차"(컬처/반차), "행위"(항생제 투여),
  "추석"(석션/명절), "음료수"(옴니옥스/마실 것), "티켓"(티피스/표). 목록과 판단 기준은
  `AMBIGUOUS_NOTES`. 규칙으로 만들면 반드시 오교정이 난다.
- **반복 환각(A 갈래).** 접기는 하되 규칙(사전 항목)으로 만들지 않는다.
- **순수 한글 오독(C 갈래).** 사전에 넣지 않는다. 사전은 임상 용어의 것이다.

## LLM 이 하는 부분

규칙으로 못 푸는 것만 넘긴다 (`apps/mobile/src/services/llm.ts`).
시스템 프롬프트가 세 덩어리이고, 뒤 둘은 요청마다 같아서 1시간 캐시된다.

1. `POST_EDIT_SYSTEM` — 무엇을 고치고 무엇을 두는지
2. `buildCorrectionRulesForLLM(lexicon)` — 확정된 오인식 대응표 + `AMBIGUOUS_NOTES`
3. `buildGlossaryForLLM(lexicon)` — 용어집

전송 전에 `redactForNetwork` 를 반드시 거친다. 줄 단위 프로토콜이라 **줄 수와 순서를 그대로**
지켜야 하고, 개인정보가 가려진 줄은 LLM 이 고쳐도 받지 않는다.

## 확정을 어디에 넣나

| 무엇 | 어디 | 왜 |
| --- | --- | --- |
| B 갈래, 2회 이상, 뜻이 하나 | `misheard.ts` + 회귀 테스트 | 앱이 자동으로 고친다 |
| 뜻이 갈리는 말 | `COMMON_WORDS` + `AMBIGUOUS_NOTES` | 규칙을 막고 이유를 LLM 에게 준다 |
| 여러 어절짜리 구 | `confirmed.jsonl` | 사전 표제어가 아니다 |
| C 갈래 · A 갈래 | 사전에 넣지 않는다 | 사전은 임상 용어의 것이다 |

사전을 고치면 `node tools/sync-skill-rules.mjs` 로 `confirmed-rules.md` 를 다시 만든다.
